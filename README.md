# FireCommand v29｜AI 文字辨識、可編輯確認與部署同步

2026-09-07｜基於已交付 v28 更新。此包是完整原始碼與部署設定，尚未代為更新正式網站。實戰與練習使用相同的文字整理、確認、登錄及繪圖模組。

## 使用方式

1. 進入案件 → **SOP → 初期部署「初」→「部署」**。
2. 點開「文字回報 → 人員、部署與紀錄」。此區預設收合，已移除案件首頁的快速回報大按鈕。
3. 輸入現場敘述；不方便打字時使用手機鍵盤內建語音轉文字。v29 已移除 App 自建收音、麥克風權限及 SpeechRecognition。
4. 點「AI 辨識內容」。系統使用已設定的 OpenAI／Gemini 整理語意，顯示實際服務與模型；不直接改資料。
5. 在每張卡片直接修改分隊、人數、增減方式、編組、車號、面向、水線終點或紀錄。漏辨識時按「新增可編輯項目」。
6. 不明項目預設「稍後處理」。修正後，勾選「已核對原句並確認此項」及「列入本次登錄」；也可先儲存其他清楚項目。
7. 核對本次總人數與差異，勾選總確認，按「確認登錄並同步」。人員名冊、部署圖、SOP、概要與紀錄共用同一組資料。

輸入新回報不必重述全部現場。**「修正為九人」是總數九人；「增加兩人」是在既有數量加二。** 未提及的其他單位、任務與位置保留。人員移位維持原 ID 與人數。

## 這版修正的根因

v28 的快速回報主要採固定句型規則，並沒有用 AI 理解整段語意；只修正幾個數字正規表示式不足以解決多單位、跨句部署與支援敘述。v29 新增真正的 AI 結構化辨識 API，另保留明確標示「非 AI」的本機整理及手動新增，供服務無法使用時操作。

v28 的不明項目只顯示提示，缺乏完整編輯欄位，且任何不明項目都會擋住整批登錄。v29 採逐項選入與直接編輯，支援「先登錄已確認資料，待確認內容留在歷史紀錄繼續處理」。按鈕無法送出時會標示具體欄位錯誤；也可按「以最新資料重新核對」，保留人工修改並對照最新現況。

## 您的例子會如何處理

| 輸入 | 登錄結果／待確認 |
|---|---|
| 淡水分隊七人、竹圍分隊六人、三芝分隊三人到場 | 三筆人員，合計 16 人；沒有位置則先放待部署區 |
| 淡水人數修正為九人 | 更新原淡水編組；若原先 7 人，變為 9 人 |
| 竹圍新增兩人 | 既有 6 人變為 8 人；不新增一個重複編組 |
| 主委、竹園、但水等同音字 | 依分隊字典、AI 與上下文提出校正；原文及校正皆可核對 |
| 已完成指揮權轉移 | 核對後更新 SOP 指揮權欄位 |
| 火場正面為第一面 | 更新 SOP 面向設定；不推定建物的地理旋轉角度 |
| 需要石台水庫車支援 | 「石台」數量不清楚，保留待確認；不猜十台，不建立已到場車輛 |
| 現場水源不足 | 登錄情資，出現在部署／概要摘要與操作紀錄 |
| 淡水第一面一線，未說車號 | 可畫橘色虛線示意，標示「供水起點待確認」；不捏造車輛 |
| 淡水11第一面一線，補上來源 | 若有同分隊、同終點的待確認線，沿用原水線 ID 補接來源 |
| 竹圍由第二面不宜先進入 | 不能當成已完成內攻；列為情資或要求核對 |

不同編組不可任意合併。當同分隊已有多個編組，需指定編組或在下拉選單選擇此次修改的對象。

## AI 設定

請先看 **[AI_SETUP_v29.html](AI_SETUP_v29.html)**（手機可閱讀）或 **[AI_SETUP_v29.md](AI_SETUP_v29.md)**。需要管理者把 API 金鑰放到 Vercel 專案環境變數，不能填入前端程式，也不需要把密鑰交到對話中。

- OpenAI：`OPENAI_API_KEY`；預設模型 `gpt-4.1-mini`。
- Gemini：`GEMINI_API_KEY`；預設模型 `gemini-2.5-flash`。
- 可設定 `AI_PRIMARY_PROVIDER`、`AI_FALLBACK_ENABLED` 與各家備用模型。
- 「AI 服務與備援設定」可選本次優先服務、停用跨服務備援、檢查設定、開啟指南。
- 服務失敗時有界重試，最多三次；仍失敗則保留文字，使用者可選本機整理或手動新增。
- ChatGPT 訂閱與 OpenAI API 分開計費；Google AI／Gemini 聊天訂閱也不等同於這個 App 的 API 無限額度。詳見設定指南的官方來源。

## 部署更新

1. 將此資料夾內容更新至原 Vercel 專案的根目錄；不要只更新 `index.html`。必須一併更新 `assets`、`api`、`server`、`firebase` 與 `vercel.json`。
2. 保留您的 Firebase 與地圖設定；新增／確認上述 AI 環境變數，重新部署才會生效。
3. 從本資料夾發布規則：

   ```sh
   firebase deploy --only firestore:rules --project firecommand-online
   ```

   若您的 Firebase 專案 ID 不同，替換成實際 ID。v29 的確認原文上限由 3,000 調整為 6,000 字，規則需同步更新；不要放寬成公開讀寫。
4. 本包 `vercel.json` 設定 AI Function 上限 90 秒；請確認專案使用支援此時限的執行設定（建議確認 Fluid Compute）。程式的模型階段總預算約 48 秒，另加登入驗證；不是保證回應時間。
5. 開啟正式首頁，確認頁首顯示 **v29**；`/api/maps-config` 顯示版本 `29`。協作人員皆重新載入，避免混用舊版本。
6. 依 **VALIDATION_v29.md** 在測試案件驗收：真實 API、iPhone 直橫式、桌機、多帳號及圖面連動。

## 登入問題

保留 v28 的 Google Identity Services 直接憑證登入與 Firebase 儲存降級，不重新引入 `signInWithRedirect`。若尚未設定公開的 `GOOGLE_IDENTITY_CLIENT_ID`，請依 **LOGIN_v28.md** 完成 Google／Firebase 網域設定；AI 金鑰不能修復登入網域設定。

如果現在停留在 `firebaseapp.com/__/auth/handler` 的舊錯誤頁，需關閉舊頁並從正式 App 首頁登入。更新 App 程式無法改寫另一網域上的 Firebase 已載入錯誤頁。本次未操作您的 Google Console，不能宣稱線上登入已完全排除。

## 資料與限制

確認前都是草稿。確認後以單一交易更新人車水線、SOP 差異與稽核紀錄；同一命令重送不重複建立。若有人先改了相關資料，拒絕覆蓋並請重新核對。復原時保留紀錄，有後續修改則不強行覆蓋。待確認項目在最近回報內可繼續處理。

繪圖使用可編輯的結構化人車水線，並非生成一張不可編輯的圖片。地理位置為示意；建物角度、消防栓精確位置、樓層內部詳細走線等仍需原有圖面工具確認。AI 不能從未提供的文字推得這些事實。支援需求不等於到場，預定動作不等於完成，安全確認不會自動打勾。

本次已完成自動測試與靜態結構檢查。**未使用真實付費 API、未連線正式 Firebase、未進行 iPhone 真機或瀏覽器視覺驗收**；不能把模擬 API 通過等同於實際辨識準確率。完整範圍見 VALIDATION_v29.md。
